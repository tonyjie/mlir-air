2Three parts, one pipeline

Vision-Language Model (left) = our ① SigLIP vision encoder + ② SmolLM2-360M backbone. Both are self-attention, non-causal, and run once.
Action Expert (right) = ③ 16 layers alternating self-/cross-attention — this is self_attn_every_n_layers=2 in the config, and it reads the VLM's frozen K/V on every one of its 10 denoise steps.
✂ the scissors mark where SmolVLA truncates a full VLM down to SmolLM2's first 16 layers — the language stack we ship is a fraction of a full model, by design.

4Do we have the kernels?

An NPU is a grid built for matmul; mlir-air compiles to it. The kernel_registry holds kernels already validated for LLM-shaped deployment.

GapResolution
Backbone's prefix-LM mask doesn't fit FlashAttention's causal on/off switchmasked-softmax — built from scratch
Vision needs affine LayerNorm and GELU-tanhpromoted into the shared registry
Conv2d patch-embed, pixel-shufflesolved as im2col + existing GEMM / host reshape — no new kernel
Net result: every kernel both stages need is now validated on real NPU2. Progress since has been gated by integration and validation effort, not by missing kernels.

5What ships — and what's just verified

StageShare of CPU runtimeOn the NPU?
① Vision59.8%✅ ships on NPU
② Backbone8.5%ported + verified — 3× slower on NPU, stays on CPU
③ Action expert31.2%ported + verified — 4× slower on NPU, stays on CPU
All three stages were ported to the NPU and independently verified. Only vision is measurably faster there — that is the only stage that ships on-chip. Shipping the winner, not maximum NPU coverage, is the whole strategy.

Fusion made vision cheap enough to win: per image, kernel launches collapse 121 → 38 dispatches (368 → 141.6 ms). Each dispatch costs roughly the same fixed overhead regardless of the work inside it — fewer, fatter dispatches is what let vision come out ahead.

Honesty check. The gate runs on an all-zero input, which is an easy case. Read plainly, that would suggest a ~10×/13× margin over threshold — but computed honestly, the real margin is ~2.6× on cosine and ~4× on nMSE. Still comfortably passing, just not as padded as the naive number implies.

Bonus: flow matching is self-correcting. The small bf16 deviation introduced per layer does not compound over the 10 denoise steps — similarity actually rises across the loop.

8Why: it comes down to shape

An NPU is a grid of compute tiles. An operation only wins if it's big enough to fill it — same kernel, same silicon, only the shape changes.

Vision
seq 1024
peak 8898
3798–5790 GFLOP/s beats CPU
Backbone
seq 256
2046–3366 GFLOP/s loses ~3×
Action expert
seq 50
25–1163 GFLOP/s loses ~4×
Vision's 1024-token sequences and 3072-wide MLPs saturate the array. The backbone's 256 tokens and the expert's 50 don't — no amount of scheduling or fusion rescues a matmul that's just too small.

9The expert isn't "4× slower" — attention is

Operation familyNPU vs CPUShare of NPU time
attention (QKᵀ, P@V, softmax, mask, GQA expand)12.6× slower56%
matmul — the 7 projections1.21× slower17%
RMSNorm3.0× slower5%
RoPE1.19× slower3%
element-wise add / SiLU-and-Mul~4–8× slower5%
Why attention specifically: only 197 of 241 prefix tokens are real — the rest is padding — so both self- and cross-attention need a genuine mask. FlashAttention can't apply one, so attention decomposes into 11 tiny dispatches per layer at seq=50, which can't fill the array either.

Even fixing that, the expert would still lose: 50 tokens pad to 64, filling only half the compute array, and every launch pays ~85 µs of fixed cost regardless of size.

10Where we are, and two lessons

  • ✅ Complete policy is faster on NPU than CPU — 1.07×, both processors at max performance
  • ✅ Same actions — cosine 0.9990, nMSE 0.0030 vs. the real CPU model
  • ✅ All three stages ported and verified; only vision ships (the honest, measured choice)
  • ✅ Vision is now NPU-bound (91% device time), not host-bound
  • ✅ 2 kernels promoted into the shared registry, 1 written from scratch, dozens of new (kernel, shape) rows validated on real NPU2
Lesson 1Maximum NPU coverage ≠ maximum speed. We ship the stage that wins, not every stage we ported.
Lesson 2A rigorous projection is still not a measurement. The expert's per-kernel estimate landed 2.5× off because two of its inputs — an assumed-usable FlashAttention, no fusion penalty — turned out false.

·In one sentence

SmolVLA's vision encoder — the largest block of compute in a vision-language-action robot policy — now runs entirely on the AMD NPU2, making the complete policy 1.07× faster than the pure-CPU model, with both processors at maximum performance, while producing the same actions (0.9990 similarity). The backbone and action expert are ported and verified too, and stay on the CPU for the honest reason that they're faster there — a decision we could only make because every stage was measured on both.
