Part A — The SmolVLA model A quick recap before we get to the NPU.

1. What is SmolVLA?

SmolVLA is a Vision-Language-Action model (VLA) — think of it as a robot's brain, from Hugging Face's LeRobot ecosystem.

In one sentence: tell a robot arm "pick up the cube" and show it a few camera views. SmolVLA reads the images + that sentence + the robot's current pose, and outputs the next 50 steps of motion (joint angles, gripper open/close). It fuses "see + understand + decide how to move" into one model.
Inputs / outputs (the lerobot/smolvla_base checkpoint, 450M params):
  • Inputs: 3 camera images + one natural-language instruction + a robot-state vector
  • Output: an "action chunk" — the next 50 steps of actions, predicted at once

Actions come from flow matching: starting from random noise, the model iteratively "denoises" over 10 steps into a coherent set of actions — the same idea as diffusion image generators, except what's being "drawn" here is robot motion.

2. Architecture, at a glance

SmolVLA is three blocks chained like a pipeline: a frozen vision encoder, a compact language backbone that fuses everything into one understanding, and an action expert that denoises that understanding into motion.

  • Vision-Language Model (left box) = our ① SigLIP vision encoder + ② SmolLM2-360M backbone. Both are self-attention, non-causal, and run once per inference.
  • Action Expert (right box) = ③ 16 layers alternating self-/cross-attention — this is self_attn_every_n_layers=2 in the config, and it reads the VLM's frozen K/V on every one of its 10 denoise steps.
  • ✂ the scissors in the diagram mark where SmolVLA truncates a full VLM down to SmolLM2's first 16 layers only — the language stack we ship is a fraction of a full model, by design.

Part B — Running it on the NPU What we ported, what we measured, and the reasoning behind what ships.

4. Do we have the kernels?

An NPU2 is a grid of compute tiles; mlir-air compiles to it. The kernel_registry holds kernels already validated for LLM-shaped deployment — but "do we have the kernel" isn't yes/no. Every operation SmolVLA needs falls into one of three buckets, and the buckets are what cost very different amounts of effort.

✓ in registry = already validated for LLM deployment — reused as-is, no extra work · ◐ existing example = a kernel already existed in programming_examples/, but at a different shape, dtype, or feature set — needed re-validating (sometimes extending) before it could be trusted at SmolVLA's own numbers · ✗ truly new = no implementation existed anywhere — built from scratch for this project.

matmul / Linear (GEMM, prefill)✓ in registrydirect reuse — 256×960×960 (Q/O), 256×960×320 (K/V), 256×960×2560 (MLP) are all shapes the registry already covers

RoPE✓ in registrydirect reuse, head_dim=64, θ=10000

element-wise add (residual)✓ in registrydirect reuse, 256×960

pixel-shuffle (space-to-depth)✓ solved as reshapepure index remap, done on the host — no kernel needed
bidirectional attention (vision)✓ in registrydirect reuse of the registry FlashAttention's non-causal mode at a new shape (1024×1024, 12/12 heads) — validated, no code changes
FlashAttention for the backbone◐ needs adjustmentthe kernel itself is in the registry, but its mask is a binary causal on/off switch, and the backbone's prefix-LM mask is neither — so it can't be reused as-is. The fix was to not force-fit it, and instead decompose attention into GEMM + a new masked-softmax + GEMM (below)
masked softmax (arbitrary host mask)✗ truly newbuilt from scratch this project — (15,256,256) scores, batched over heads
GELU-tanh◐ existing example, promotedexisted in programming_examples/gelu but hadn't been validated at an LLM-deployment shape; validated at (1,1024,3072) (24.1 GB/s) and promoted into the registry
LayerNorm (affine γ,β)◐ existing example, promotedlayer_norm/ existed but without the affine parameters or multi-tile support SmolVLA needs; extended, validated at (1,1024,768) (rel. error 4.4e-3), and promoted into the registry
Net result: every kernel both the vision and backbone stages need is now validated on real NPU2. Of the two "new work" rows, one was a genuine gap (masked-softmax) and one was recognizing that an existing kernel's assumptions didn't hold and needed a different decomposition, not a rewrite (FlashAttention). Everything else was already in the registry, or was an existing example that just needed validating at SmolVLA's own shapes. Progress since has been gated by integration and measurement effort, not by missing kernels.

What one layer actually dispatches

[NPU elf:…] = one compiled program = one dispatch to the chip; FUSED means several operations were merged into that single program. (HOST) = runs on CPU.

① VISION — one of 12 layers 3 dispatches/layer once per image, before layer 0: (HOST) im2col patch-embed + position-embedding → x [1024,768] ─[NPU elf:vit_ln_qkv] FUSED, 7 launches { LayerNorm1 + Q + K + V GEMM + biases } ─[NPU elf:flash_attn] bidirectional MHA [1024,1024], 12 heads, scale 1/8 ─[NPU elf:vit_o_ffn] FUSED, 10 launches { O + residual + LayerNorm2 + fc1 + GELU + fc2 + residual } → layer_out [1024,768] once after 12 layers: [NPU elf:layer_norm] post_layernorm once per image: (HOST) pixel-shuffle → [NPU elf:gemm_connector] 64×12288×960 → 38 dispatches per image · 114 for all 3 cameras ② BACKBONE — one of 16 layers 13 dispatches/layer x [256,960] ─[NPU elf:rms_gemms_rope] FUSED, 6 launches { RMSNorm + Q/K/V GEMM + RoPE-Q + RoPE-K } ─attention NOT fused — 11 dispatches (HOST) reshape to heads, transpose Kᵀ, fold in the prefix-LM mask 5× [NPU elf:qkt] · 1× [NPU elf:masked_softmax] · 5× [NPU elf:pv] ─[NPU elf:o_ffn] FUSED, 8 launches { O + Add + RMSNorm + Gate + Up + SwiGLU + Down + Add } → layer_out [256,960] once after 16 layers: (HOST) final RMSNorm → 208 dispatches per inference
Fusion, not just kernel choice, decided the winner. Vision was fused: 12 layers cost only 38 dispatches. The backbone's attention wasn't: its 11 unfused dispatches/layer make 208 in total, on a stage 8× smaller than vision. Since each dispatch costs roughly the same fixed overhead regardless of how much work it carries, the backbone pays that toll ~5× more often for far less compute. Per image, fusion collapsed vision's launches 121 → 38 dispatches (368 → 141.6 ms).

6. Why performance looks like this

An NPU2 is a grid of compute tiles. An operation only wins if it's big enough to fill it — same kernel, same silicon, only the shape changes.

Three operations carry the whole win — and five kernels quietly give part of it back. Attention alone saves 2.9 ms of the 4.0 ms gained per layer, fc2 and fc1 another 1.9 ms — that's the entire per-layer speedup. Against that, everything memory-bound (LayerNorm, the residual adds) runs the wrong way; and because PyTorch folds bias into nn.Linear while the NPU launches a separate kernel for each, those bias kernels alone cost 1100 µs per layer (10.5%) against a CPU counterpart of zero. Scaled up: 10.5 ms × 12 layers = 126.2 ms vs. 134.5 ms deployed — the 8.3 ms gap is the cost of switching between the layer's three fused programs.

Note the Q/K/V rows: the same 1024×768×768 matmul as fc1/fc2 in kind, yet they lose while fc1/fc2 win. The difference is width — fc1 writes 3072 values and fc2 reduces over 3072, filling the compute array; 768×768 does not. "Matmuls are fast on an NPU" holds only once they are big enough — which is exactly the story the shape chart below tells at the whole-stage level.

  • ✅ Same actions — cosine 0.9990, nMSE 0.0030 vs. the real CPU model
  • ✅ All three stages ported and verified; only vision ships (the honest, measured choice)
  • ✅ Vision is now NPU-bound (91% device time), not host-bound

What's next: generalizing beyond SmolVLA

The bigger opportunity isn't squeezing more out of this one 450M-parameter model — it's applying the same mapping to other, larger VLA models. A bigger backbone or a bigger expert means bigger matmuls, and bigger matmuls are exactly what an NPU2 rewards; the case for the NPU should only get stronger as these policies scale up.

Why VLA is harder than a plain LLM, though. A VLA policy has more, and more heterogeneous, moving parts than a language model alone — a vision encoder, a connector, a language backbone, and a flow-matching expert, stitched together with host-side glue like concatenating vision/language/state tokens into one prefix. Two consequences follow from that: (1) some of today's kernels aren't general enough to carry those seam operations efficiently on-chip — they were built for the block computation, not the glue between blocks — and (2) those same seams raise the bar for fully fusing a whole stage into one dispatch, which is exactly the lever that made vision win here.

Closer to home, incremental headroom also remains in today's mapping:

The backbone and action expert are ported and verified too, and stay on the CPU for the honest reason that they're faster there — a decision we could only make because every stage was measured on both.
