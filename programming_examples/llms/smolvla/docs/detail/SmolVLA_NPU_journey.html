Part A — The SmolVLA model Understanding the model itself and its CPU behavior. Nothing about the NPU yet.

1. What is SmolVLA?

SmolVLA is a Vision-Language-Action model (VLA) — think of it as a robot's brain. It comes from Hugging Face's LeRobot ecosystem.

In one sentence: you tell a robot arm "pick up the cube" and give it a few camera views. SmolVLA reads the images + that sentence + the robot's current pose, and outputs a sequence of moves to make next (joint angles, gripper open/close). It fuses "see + understand + decide how to move" into one model.
Inputs / outputs (the lerobot/smolvla_base checkpoint, 450M params):
  • Inputs: 3 camera images + one natural-language instruction + a robot-state vector
  • Output: an "action chunk" — it predicts the next 50 steps of actions at once

It generates actions with a method called flow matching: starting from random noise, it iteratively "denoises" over 10 steps into a coherent set of actions — similar to how AI image generators use diffusion, except here what's being "drawn" is robot motion.

2. The three parts of the model

Inside, SmolVLA is three blocks chained like a pipeline:

Why is the backbone a "language model"?

SmolVLA's second block is really a compact large-language model (SmolLM2-360M, same family as Llama). The difference: it doesn't "speak" (it generates no text). Instead it reads the images, text, and state all at once, understands them in a single pass, and hands an "understanding" to the action expert.

How all THREE conditioning inputs become tokens (verified)

A common confusion: the vision encoder handles images — but what about the instruction and the state? All three are turned into tokens (fixed-width vectors) and concatenated into one sequence called the prefix. Here is the exact, source-verified flow:

InputModule that embeds itShape flowResult
3 camera images embed_image = SigLIP ViT → connector (see below) (3,3,512,512) → per image (64,960) 3 × 64 = 192 vision tokens
Instruction text embed_language_tokens = a token-embedding lookup table tokenizer → (1,48) ids → (48,960) 48 language tokens
Robot state state_proj = a single Linear (1,32) → (1,960) 1 state token
Concatenate → the prefix fed to the backbone: (241,960)

So the backbone doesn't just see images — it sees images + words + state as one 241-token sequence. The attention mask (verified in embed_prefix) makes image + language tokens attend to each other bidirectionally, while the state token starts a new block — i.e. the backbone's attention is "non-causal."

How attention works (read once — the tables below use this notation)

All three stages use the same attention recipe; only three things change between them: the sequence lengths, where K/V come from, and the mask. Given an input of (seq, d), one attention does:

  1. Project to Q, K, V (three matmuls with learned weights), then split into h heads of width head_dim: Q → (h, seq_q, head_dim),   K, V → (h, seq_k, head_dim).
  2. Scores = Q · Kᵀ / √head_dim → (h, seq_q, seq_k) — row i, col j = "how much query token i attends to key token j."
  3. Mask + softmax over the last axis (seq_k): add the mask (0 = visible, −∞ = hidden), then softmax so each row sums to 1 → (h, seq_q, seq_k).
  4. Weighted sum of V: P · V → (h, seq_q, head_dim), concat heads → (seq_q, h·head_dim), then an output projection (O-proj).

Shorthand used below: Q seq_q × K seq_k → scores (seq_q, seq_k). self-attention = K/V come from the same tokens as Q (so seq_q = seq_k); cross-attention = K/V come from a different source (seq_q ≠ seq_k). GQA (grouped-query): fewer K/V heads than Q heads, so K/V-proj is narrower — several Q heads share one K/V head.

The three masks, concretely: SigLIP = no mask (all 1024 patches see each other). backbone = a (241,241) prefix-LM mask — the top-left 240×240 block is all-visible (0), and only the state column (the 241st) is −∞ for the first 240 rows (prefix can't see state; state sees everything). expert self-attn = causal among the 50 action tokens; expert cross-attn = no mask (all 50 actions attend to all 241 prefix tokens).

4. Where the model spends its time (CPU profiling)

Before touching any accelerator, we profiled the real CPU baseline — the unmodified lerobot/smolvla_base running its own predict_action_chunk (a true reference, not a reimplementation). The loaded weights are already bfloat16 (474 bf16 + 26 fp32 tensors, the fp32 ones being norms / state_proj). One action chunk takes ~1044 ms on CPU.

StageCPU time / chunkShareRuns per chunk
① vision (SigLIP)719 ms73.6%1×
①b connector4.5 ms0.5%1×
② backbone56.8 ms5.8%1×
③ action expert196.8 ms20.1%10× (denoise loop)

By operation type across the whole model: matmul 55% · attention 36% · norm 4.4% · activation 3.7% · conv 0.4%.

The surprising bottleneck: vision (73.6%). Nearly three-quarters of the time is the SigLIP vision encoder — because its attention matrix is large (1024×1024) and it has 12 layers. The language backbone, despite being the "main" model, is only 5.8% (it runs just once). The action expert is 20.1% because it runs 10 times in the denoise loop. This breakdown tells us where acceleration would matter most — a fact we return to in Part B.

5. Why an NPU, and which kernels we already have

CPU vs NPU analogy: a CPU is a versatile generalist — it can compute anything, but only so much at once. An NPU (Neural Processing Unit) is like a workshop built for matrix multiplication — and most of an AI model's compute is exactly that. A robot needs to react in real time, so moving the model onto an NPU is a key step. Our chip is the AMD NPU2 (Strix, AIE2P); the compiler is mlir-air.

A "kernel" is a low-level operation compiled to run on the NPU. Two sources matter here: (1) the kernel_registry — kernels curated and shape-validated for LLM deployment (GEMM bf16→fp32 & bf16→bf16, GEMV, RMSNorm, FlashAttention, Element-wise Add, SiLU-and-Mul, RoPE, and — added during the A3 vision work below — LayerNorm and GELU-tanh, now 9 kernel families); and (2) the wider programming_examples/ tree, which has additional kernels that exist but haven't been through the registry's LLM-deployment validation. So each SmolVLA operation falls into one of three tiers, not just "have / don't have":

Why not use the existing FlashAttention kernel for the backbone? The registry FA kernel does support both causal and non-causal attention, GQA, and head_dim 64 — so this is a fair question. But two things make it a poor fit for SmolVLA's backbone:
  • Its mask is a single boolean switch (causal on/off), not an arbitrary mask. SmolVLA's prefix attention is neither fully causal nor fully bidirectional — it is a prefix-LM mask (240×240 visible block + the state column masked, from Part A §3). FA can't express that mixed pattern; our masked_softmax takes a host-supplied mask, so causal / bidirectional / padding-aware are all possible.
  • FA's advantage doesn't apply at this size. FA's whole point is avoiding a full score matrix for long sequences via online-softmax; its tile config is a near-fixed point tuned for seq≈2048–16384. SmolVLA's backbone is seq=241 — the full 256×256 score matrix (~262 KB) fits in on-chip L2, so a plain matmul + masked-softmax + matmul is simpler and just as fast, with no flash machinery.
(FA also has a known head_dim=128 hang risk on some NPU2 setups; SmolVLA is head_dim=64, so that one doesn't apply.)
This table decided the strategy — and the gap has since been closed. The backbone was entirely tier-1 (registry) plus the one masked-softmax we wrote, so it moved to the NPU first. The vision stage then needed no from-scratch kernels either: GELU-tanh and LayerNorm were validated and promoted into the registry, conv2d turned out to be im2col + an existing GEMM, pixel-shuffle is a host reshape, and the large 1024×1024 attention ran on the registry FlashAttention (its even 12 heads even fill the whole array). So every kernel both stages need is now validated on real NPU2, and both stages run there — the next section shows exactly how. The action expert, still on the CPU, reuses the backbone's kernels at smaller shapes; its sin/cos already has an example too. Net: progress is gated by integration and validation effort, not by missing kernels.

6. What runs on the NPU today

SmolVLA's vision encoder — the single biggest block of compute in the model — runs entirely on the NPU, and that is what makes the whole policy faster than the CPU (Section 8). The language backbone is also fully ported and verified, but it measured slower on the NPU, so the shipping configuration leaves it on the CPU. This section is the single picture of what sits where; the two after it give the accuracy and the speed.

StageWhat it isShare of CPU runtimeOn the NPU?
① Vision (SigLIP)12-layer ViT, run once per camera (×3)~69%✅ fully on NPU
①b Connectorpixel-shuffle + projection into the language space~0.5%✅ on NPU (the projection; the shuffle is a host reshape)
② Backbone (SmolLM2-360M)16-layer transformer prefill~9%CPU by choice — a full NPU port exists and is verified, but is 2.6× slower there (Section 9)
③ Action expert16 layers × 10 denoising steps~32%CPU — not ported

Percentages are of the measured pure-CPU predict_action_chunk (Section 8's harness). Inside stages ① / ①b every matmul, norm, attention and activation executes on the NPU — there is no CPU fallback; the host only does data-shuffling glue (see below).

Why the backbone runs on the CPU even though we ported it. We mapped all 16 backbone layers onto the NPU and verified them (that port still passes its own gate and is one flag away). But measured head-to-head it is 229 ms on the NPU vs 91 ms on the CPU — the NPU loses on this stage, for reasons Section 9 explains. Our goal is a genuinely faster robot policy, not maximum NPU coverage, so the shipping configuration puts the vision encoder on the NPU and leaves the backbone where it is fastest. Keeping it on the CPU also removes a redundancy: the pipeline no longer has to compute the backbone twice and overwrite the result.

What one layer actually dispatches

[NPU elf:…] = one compiled program = one dispatch to the chip; FUSED means several operations were merged into that single program. (HOST) = runs on CPU. The contrast between the two stages is the key to Section 9's performance story.

① VISION — one of 12 layers 3 dispatches/layer once per image, before layer 0: (HOST) im2col patch-embed + position-embedding → x [1024,768] ─[NPU elf:vit_ln_qkv] FUSED, 7 launches { LayerNorm1 + Q + K + V GEMM + biases } ─[NPU elf:flash_attn] bidirectional MHA [1024,1024], 12 heads, scale 1/8 ─[NPU elf:vit_o_ffn] FUSED, 10 launches { O + residual + LayerNorm2 + fc1 + GELU + fc2 + residual } → layer_out [1024,768] once after 12 layers: [NPU elf:layer_norm] post_layernorm once per image: (HOST) pixel-shuffle → [NPU elf:gemm_connector] 64×12288×960 → 38 dispatches per image · 114 for all 3 cameras ② BACKBONE — one of 16 layers 13 dispatches/layer x [256,960] ─[NPU elf:rms_gemms_rope] FUSED, 6 launches { RMSNorm + Q/K/V GEMM + RoPE-Q + RoPE-K } ─attention NOT fused — 11 dispatches (HOST) reshape to heads, transpose Kᵀ, fold in the prefix-LM mask 5× [NPU elf:qkt] · 1× [NPU elf:masked_softmax] · 5× [NPU elf:pv] ─[NPU elf:o_ffn] FUSED, 8 launches { O + Add + RMSNorm + Gate + Up + SwiGLU + Down + Add } → layer_out [256,960] once after 16 layers: (HOST) final RMSNorm → 208 dispatches per inference
Read this comparison — it explains almost everything in Section 9. Vision was fused: 12 layers cost only 38 dispatches. The backbone's attention was not: its 11 unfused dispatches per layer make 208 in total, on a stage that is 8× smaller than vision. Since each dispatch costs roughly the same fixed overhead regardless of how much work it carries, the backbone pays that toll ~5× more often for far less compute.

What stays on the host, and why it isn't a fallback

  • im2col (once per image) and pixel-shuffle (once per image) — pure index reshuffles with zero arithmetic; running them on the NPU would cost more in data movement than it saves.
  • The backbone's attention glue — reshaping to heads, transposing Kᵀ, folding the mask into the score buffer. This is a consequence of attention not being fused, and disappears if it is.
  • One final RMSNorm after layer 16 (outside the hot loop, consistent with the sibling deployments).
  • The whole action expert — by design, not yet started.

7. Correctness: does it still produce the right actions?

"Correct" for a robot policy can mean two different things, and they are not interchangeable:

QuestionReferenceName
Did moving to the NPU introduce a bug or precision loss?the real CPU model (lerobot PyTorch)port fidelity
Does the model produce good robot actions?ground-truth recorded trajectoriestask fidelity

Our job is a port: move the computation to the NPU without damaging it. So the reference that matters is the real CPU model — matching it proves "we didn't break it." (The CPU model itself isn't a perfect policy; task fidelity would need the LIBERO-finetuned checkpoint, discussed at the end of this section.)

How it was built: every step verified before the next

Both stages were brought up the same way, and the ordering is the reason the port is trustworthy: ① dump a CPU "answer key" from the real model → ② validate each kernel alone at SmolVLA's exact shapes → ③ assemble one layer and compare → ④ scale to all layers → ⑤ run end-to-end and compare the action chunk. A mismatch at any step is localized to what was just added.

This caught things a final end-to-end check never would have. Example: the model's config says the RoPE parameter is 100000, but the code actually uses 10000 at runtime — visible only by comparing a single layer against the answer key. Silently wrong, and it would have corrupted the whole backbone.

Gate thresholds: cosine ≥ 0.99 and normalized MSE ≤ 0.04, on the full (50, 6) action chunk with fixed noise so the comparison is deterministic. The shipping configuration scores highest because the vision encoder is then the only source of NPU-induced deviation. All three configurations pass, and the two that include the NPU backbone are bit-identical to each other — which is how we check that a refactor did not change the maths. The per-layer checks are diagnosis, never the gate: an earlier experiment passed every layer yet failed end-to-end, so only the action chunk decides.

The port is verified end-to-end against the real model. With both the vision encoder and the language backbone on the NPU, the produced action chunk still matches the pure-CPU lerobot output at 0.994 similarity — inside the gate with room to spare.

What this metric does not tell us

  • Cosine is scale-blind, and these are physical outputs. A systematically scaled action would still score well. We also report normalized MSE for that reason, but per-dimension error would be stricter.
  • One input. The gate uses a single synthetic observation, so it cannot catch input-dependent effects.
  • Thresholds are engineering, not physics. 0.99 was set from what a clean run achieves, not from "the robot still completes the task."
  • No ground truth. The base checkpoint has no recorded trajectories to score against. Getting true task fidelity means porting to the LIBERO-finetuned checkpoint — mechanically cheap (the backbone dimensions are identical, so the kernels and fused programs carry over unchanged; it is 32 layers instead of 16 and 2 cameras instead of 3).

What made this possible: removing the two-process bridge

An earlier version ran the NPU stages as separate subprocesses, because our CPU and NPU code were assumed to need different Python environments. They do not — one environment can host both. Collapsing to a single process lets the weights, the compiled programs and the device context load once at startup instead of on every inference:

A tuning detail that mattered more than expected. The numerical library's worker threads keep spinning after the one host-side matmul in the vision path, stealing CPU from the thread that issues NPU work — inflating the encoder from 135 ms to 178 ms per image. Capping those threads only around the NPU section and restoring them afterwards recovers it without hurting the thread-hungry action expert: 874 ms with the cap vs 962 ms without, and the expert stage is unaffected (305 ms either way).

9. Why the performance looks like this

Three effects explain the whole picture. The first is a property of the hardware; the other two are things we have not finished doing.

① Big shapes win, small shapes lose — this is the hardware's nature

An NPU is a large grid of compute tiles. Efficiency depends on whether a given operation has enough work to fill that grid. Vision and the backbone sit on opposite sides of that line:

Kernel, at the shape we actually useNPUCPU
Matmul at vision size (1024×768×768)3798 GFLOP/s—array well fed
Matmul at backbone size (256×960×960)1896 GFLOP/s—half the efficiency
Attention at vision size (1024², 12 heads)1292 GFLOP/s—fills the full grid
Attention at backbone size (256², 15 heads)280 GFLOP/s~500 GFLOP/sNPU loses to CPU

The backbone's attention is the worst case: its sequence is short and its 15 heads are an odd number, which forces the kernel onto half the grid (an even head count, like vision's 12, packs two per unit and fills it — measured 1.58× just from that). For reference the same matmul kernel reaches 8898 GFLOP/s at large sizes, so the backbone shapes run at roughly a fifth of the chip's capability.

② The backbone's attention was never fused — 208 dispatches

Every dispatch to the chip carries a fixed cost (~1.75 ms of driver and Python overhead) regardless of how much work it does. We measured this directly on the vision encoder before it was optimized: of its total time, only 141 ms was real NPU compute and 212 ms was pure dispatch overhead across 121 dispatches. It was host-bound, not compute-bound.

Fusing vision's operations into merged programs fixed exactly that:

A surprise worth recording: fusing for speed also fixed accuracy. Before fusion the 12 layers in sequence only reached 0.945 similarity, and we had accepted that as a hardware precision ceiling — the NPU's fast matmul format (a block of numbers sharing one exponent) leaves a small systematic bias, and unlike random noise, systematic bias accumulates coherently across layers. Fusion removed it as a side effect: doing the small additions on-chip eliminated a host round-trip that had been amplifying that bias each layer. Accuracy went to 0.990 and passed. An apparent hardware limit turned out to be an artifact of how the pipeline was assembled.

The backbone has not had this treatment. Its attention is still 11 separate dispatches per layer — 208 in total, versus vision's 38 per image — on a stage with far less compute to amortize them. That is the single clearest explanation for why our backbone is 2.5× slower than the CPU's, and the most promising thing left to fix.

③ Two overheads that were not the hardware's fault (both now fixed)

  • The two-process bridge (585 ms + 568 ms per inference). Launching each NPU stage as a subprocess re-paid process startup, weight loading and device setup on every call. It turned out both halves can live in one Python environment, so this is simply gone (Section 8).
  • A redundant CPU backbone (~91 ms). When the NPU ran the backbone, the CPU still computed its own copy first and we overwrote the result. Keeping the backbone on the CPU removed the duplication entirely.
  • Thread contention that looked like an NPU problem. The numerical library's workers kept spinning after the one host matmul and stole CPU from the thread issuing NPU work — 135 ms → 178 ms per image. The giveaway was misleading: the same kernel took 139 ms on a cached array and 178 ms on a freshly computed one. Scoped thread-capping fixed it.

Worth stating plainly: of the four effects in this section, only the first is a property of the hardware. The other three were engineering — and removing them is what turned a 0.42× pipeline into a 1.11–1.29× one on exactly the same silicon and the same kernels.

What this adds up to

Vision on the NPU saves roughly 190 ms per inference; that is the whole win, and it is enough because vision is the largest block of compute in the model. The backbone would cost ~138 ms on the NPU, so it stays on the CPU. The overheads that used to dominate — over a second of process bridging — are gone. What remains on the table is real but bounded: fusing the backbone's attention (the same fix that gave vision 2.6×) could plausibly make the backbone worth moving too, and splitting the three cameras across CPU and NPU in parallel is measured to be worth about another 0.06× — at the cost of concurrency in a robot control loop.

10. Current status and next steps

Where we are

  • ✅ The complete robot policy is faster on the NPU than on the CPU — 1.11–1.29× end to end, with the vision encoder (the largest compute block) running entirely on-chip.
  • ✅ It still produces the same actions — similarity 0.9990, normalized MSE 0.0030 against the real lerobot CPU output (gate: 0.99 / 0.04).
  • ✅ The vision encoder is 1.5× faster than the CPU (147 ms vs 187–223 ms per image), after fusion cut it from 121 dispatches to 37.
  • ✅ The backbone is fully ported and verified too — but measured 2.6× slower on the NPU, so it ships on the CPU. The port is one flag away and still gated.
  • ✅ Along the way: 2 kernels promoted into the shared registry (affine LayerNorm, GELU-tanh), 1 written from scratch (masked-softmax), 17 (kernel, shape) rows validated on real NPU2, and a shared-code bug fixed with no regression to the sibling models.
The lesson we would carry to the next model. Maximum NPU coverage and maximum speed are not the same goal. Three of the four things standing between us and a win were not hardware limits — a process bridge, a duplicated computation, and thread contention — and the fourth (small shapes) is best answered by choosing which stages to move, not by moving everything. Measuring each stage on both processors, and being willing to leave one on the CPU, is what produced the speedup.
