Part A — The SmolVLA model Understanding the model itself and its CPU behavior. Nothing about the NPU yet.

1. What is SmolVLA?

SmolVLA is a Vision-Language-Action model (VLA) — think of it as a robot's brain. It comes from Hugging Face's LeRobot ecosystem.

In one sentence: you tell a robot arm "pick up the cube" and give it a few camera views. SmolVLA reads the images + that sentence + the robot's current pose, and outputs a sequence of moves to make next (joint angles, gripper open/close). It fuses "see + understand + decide how to move" into one model.
Inputs / outputs (the lerobot/smolvla_base checkpoint, 450M params):
  • Inputs: 3 camera images + one natural-language instruction + a robot-state vector
  • Output: an "action chunk" — it predicts the next 50 steps of actions at once

It generates actions with a method called flow matching: starting from random noise, it iteratively "denoises" over 10 steps into a coherent set of actions — similar to how AI image generators use diffusion, except here what's being "drawn" is robot motion.

2. The three parts of the model

Inside, SmolVLA is three blocks chained like a pipeline:

Why is the backbone a "language model"?

SmolVLA's second block is really a compact large-language model (SmolLM2-360M, same family as Llama). The difference: it doesn't "speak" (it generates no text). Instead it reads the images, text, and state all at once, understands them in a single pass, and hands an "understanding" to the action expert.

3. Full architecture: every step from input to output

This section breaks the whole pipeline down to every module, every operation, and every tensor shape. Every shape below is measured on the real checkpoint (batch = 1), and the data flow was verified against the LeRobot source (modeling_smolvla.py · embed_prefix / embed_suffix).

How all THREE conditioning inputs become tokens (verified)

A common confusion: the vision encoder handles images — but what about the instruction and the state? All three are turned into tokens (fixed-width vectors) and concatenated into one sequence called the prefix. Here is the exact, source-verified flow:

InputModule that embeds itShape flowResult
3 camera images embed_image = SigLIP ViT → connector (see below) (3,3,512,512) → per image (64,960) 3 × 64 = 192 vision tokens
Instruction text embed_language_tokens = a token-embedding lookup table tokenizer → (1,48) ids → (48,960) 48 language tokens
Robot state state_proj = a single Linear (1,32) → (1,960) 1 state token
Concatenate → the prefix fed to the backbone: (241,960)

So the backbone doesn't just see images — it sees images + words + state as one 241-token sequence. The attention mask (verified in embed_prefix) makes image + language tokens attend to each other bidirectionally, while the state token starts a new block — i.e. the backbone's attention is "non-causal."

How attention works (read once — the tables below use this notation)

All three stages use the same attention recipe; only three things change between them: the sequence lengths, where K/V come from, and the mask. Given an input of (seq, d), one attention does:

  1. Project to Q, K, V (three matmuls with learned weights), then split into h heads of width head_dim: Q → (h, seq_q, head_dim),   K, V → (h, seq_k, head_dim).
  2. Scores = Q · Kᵀ / √head_dim → (h, seq_q, seq_k) — row i, col j = "how much query token i attends to key token j."
  3. Mask + softmax over the last axis (seq_k): add the mask (0 = visible, −∞ = hidden), then softmax so each row sums to 1 → (h, seq_q, seq_k).
  4. Weighted sum of V: P · V → (h, seq_q, head_dim), concat heads → (seq_q, h·head_dim), then an output projection (O-proj).

Shorthand used below: Q seq_q × K seq_k → scores (seq_q, seq_k). self-attention = K/V come from the same tokens as Q (so seq_q = seq_k); cross-attention = K/V come from a different source (seq_q ≠ seq_k). GQA (grouped-query): fewer K/V heads than Q heads, so K/V-proj is narrower — several Q heads share one K/V head.

The three masks, concretely: SigLIP = no mask (all 1024 patches see each other). backbone = a (241,241) prefix-LM mask — the top-left 240×240 block is all-visible (0), and only the state column (the 241st) is −∞ for the first 240 rows (prefix can't see state; state sees everything). expert self-attn = causal among the 50 action tokens; expert cross-attn = no mask (all 50 actions attend to all 241 prefix tokens).

4. Where the model spends its time (CPU profiling)

Before touching any accelerator, we profiled the real CPU baseline — the unmodified lerobot/smolvla_base running its own predict_action_chunk (a true reference, not a reimplementation). The loaded weights are already bfloat16 (474 bf16 + 26 fp32 tensors, the fp32 ones being norms / state_proj). One action chunk takes ~1044 ms on CPU.

StageCPU time / chunkShareRuns per chunk
① vision (SigLIP)719 ms73.6%1×
①b connector4.5 ms0.5%1×
② backbone56.8 ms5.8%1×
③ action expert196.8 ms20.1%10× (denoise loop)

By operation type across the whole model: matmul 55% · attention 36% · norm 4.4% · activation 3.7% · conv 0.4%.

The surprising bottleneck: vision (73.6%). Nearly three-quarters of the time is the SigLIP vision encoder — because its attention matrix is large (1024×1024) and it has 12 layers. The language backbone, despite being the "main" model, is only 5.8% (it runs just once). The action expert is 20.1% because it runs 10 times in the denoise loop. This breakdown tells us where acceleration would matter most — a fact we return to in Part B.

5. Why an NPU, and which kernels we already have

CPU vs NPU analogy: a CPU is a versatile generalist — it can compute anything, but only so much at once. An NPU (Neural Processing Unit) is like a workshop built for matrix multiplication — and most of an AI model's compute is exactly that. A robot needs to react in real time, so moving the model onto an NPU is a key step. Our chip is the AMD NPU2 (Strix, AIE2P); the compiler is mlir-air.

A "kernel" is a low-level operation compiled to run on the NPU. Two sources matter here: (1) the kernel_registry — 8 kernels curated and shape-validated for LLM deployment (GEMM bf16→fp32 & bf16→bf16, GEMV, RMSNorm, FlashAttention, Element-wise Add, SiLU-and-Mul, RoPE); and (2) the wider programming_examples/ tree, which has additional kernels that exist but haven't been through the registry's LLM-deployment validation. So each SmolVLA operation falls into one of three tiers, not just "have / don't have":

Why not use the existing FlashAttention kernel for the backbone? The registry FA kernel does support both causal and non-causal attention, GQA, and head_dim 64 — so this is a fair question. But two things make it a poor fit for SmolVLA's backbone:
  • Its mask is a single boolean switch (causal on/off), not an arbitrary mask. SmolVLA's prefix attention is neither fully causal nor fully bidirectional — it is a prefix-LM mask (240×240 visible block + the state column masked, from Part A §3). FA can't express that mixed pattern; our masked_softmax takes a host-supplied mask, so causal / bidirectional / padding-aware are all possible.
  • FA's advantage doesn't apply at this size. FA's whole point is avoiding a full score matrix for long sequences via online-softmax; its tile config is a near-fixed point tuned for seq≈2048–16384. SmolVLA's backbone is seq=241 — the full 256×256 score matrix (~262 KB) fits in on-chip L2, so a plain matmul + masked-softmax + matmul is simpler and just as fast, with no flash machinery.
(FA also has a known head_dim=128 hang risk on some NPU2 setups; SmolVLA is head_dim=64, so that one doesn't apply.)
This table decides the strategy. The backbone is entirely tier-1 (registry) plus the one masked-softmax we built → it can move to the NPU now. The vision stage is mostly tier-2: GELU-tanh, LayerNorm and conv2d all have programming_examples/ implementations that need validating/adapting at SigLIP's shape/dtype — only pixel-shuffle is genuinely new (and it's just a reshape). Its remaining difficulty is the large 1024×1024 attention, not a pile of from-scratch kernels. The action expert reuses the backbone's kernels at smaller shapes; its sin/cos also already has an example. So "how much is truly new" is small — the milestones are gated more by integration + validation effort than by missing kernels.

6. Our mapping solution: the CPU / NPU hybrid

Given the kernel availability above, we built a hybrid pipeline: the NPU runs the language backbone (all its kernels exist); the CPU runs the rest. This is milestone A1.

The backbone runs seq=241 padded to 256; the GEMMs pick fused-cast vs drain per shape via gemm_registry_config (registry-driven, same mechanism as the llama/qwen siblings).

How one backbone layer actually runs on the NPU

The per-layer operations are packed into a small number of fused ELFs (one compiled NPU program that chains several kernels, so it's one XRT dispatch instead of many). The two non-attention groups reuse the exact fused ELFs built for the llama/qwen deployments; attention is host-orchestrated from 3 small kernels. Concretely, per layer (this is the make verify path, attention on NPU):

rms_gemms_rope.elf  — 1 dispatch  (RMSNorm + Q/K/V GEMM + RoPE Q/K)  reused from llama
  → attention  — 11 dispatches  (5× qkt GEMM · 1× masked_softmax · 5× pv GEMM)
  → o_ffn.elf  — 1 dispatch  (O proj + add + RMSNorm + Gate/Up + SwiGLU + Down + add)  reused from llama
= 13 XRT dispatches/layer × 16 layers = 208 total. 5 distinct ELFs compiled once + cached: rms_gemms_rope, qkt, masked_softmax, pv, o_ffn.

The attention 11 dispatches = the batched per-head design (from GQA: 15 q-heads share 5 kv-heads, so 5 qkt + 5 pv, each batching 3 heads via a stacked matmul; plus 1 masked_softmax over all heads). Compare the 2 fused non-attention ELFs — the attention is the un-fused part, and cutting those 11 dispatches is exactly what the Section 9 optimization and the future Route 3 target. (The final RMSNorm after layer 16 runs on CPU, outside the per-layer loop — same choice as the llama/qwen siblings.)

Key design: how the non-causal attention was built

The backbone's attention is a prefix-LM mask (image + text see each other both ways; the state token starts a new block). The registry FlashAttention kernel supports both causal and non-causal attention — but its mask is a single boolean switch (causal on/off), which can't express this mixed prefix-LM pattern (see the "Why not use FlashAttention" box in Section 5). And the score matrix is only 241×241 — small enough to fit on-chip, so FlashAttention's long-sequence online-softmax machinery buys nothing here. So we compose attention from three simple blocks: GEMM for Q×Kᵀ → masked_softmax (a new kernel handling all heads + an arbitrary host mask at once) → GEMM for probabilities×V. Because the mask is host-supplied, causal, bidirectional, prefix-LM, and padding-aware are all possible.

Is the whole backbone on the NPU? Yes — but only the backbone. All 16 backbone layers' compute (RMSNorm, every GEMM projection, RoPE, attention, SwiGLU) runs on NPU; only the single post-layer-16 RMSNorm stays on CPU (outside the hot loop, sibling-consistent). What is not on the NPU at all: ① the vision encoder + connector and ③ the action expert + 10-step denoise loop — these remain fully on CPU (see Section 5 for what each would need; the expert is the natural next milestone since its cross-attention already reads the backbone K/V cache the hybrid pipeline produces).

7. How we mapped the backbone (phase by phase)

Like stacking bricks, every step was verified correct before adding the next. Four phases:

0Build a CPU reference (the "answer key")

Run the real SmolVLA on CPU and record every layer's output as the oracle. Everything the NPU computes is checked against it. ✅ done

💡 This caught a trap: the config says the RoPE parameter is 100000, but the code uses 10000 at runtime — found only by comparing against the answer key. The wrong value would silently corrupt the backbone.

1Validate each kernel

Re-test the 7 existing kernels at SmolVLA's sizes, and build the one new kernel (non-causal masked softmax) from "matmul + masked softmax." ✅ done

2Assemble ONE layer

Run the backbone's first layer on the NPU, compare with the answer key: similarity 0.99998 (1.0 = identical). ✅ done

3Scale to 16 layers, run end to end

Run all 16 layers, inject the NPU K/V into the CPU action expert, produce the action chunk, compare with the pure-CPU chunk. ✅ done

💡 A "perturbation test" (replacing the NPU K/V with random noise makes the action change drastically) proves the action is genuinely driven by the NPU's computation, not the CPU.

9. Performance on the NPU (before vs after optimization)

This project was correctness-first, then optimize speed. On the first measurement the NPU backbone was slower than it needed to be — because the attention part split the 15 heads into many small jobs, so each layer issued 31 attention dispatches (15 QKᵀ + 1 softmax + 15 PV) on top of the 2 fused ELFs = 33/layer, and the job-launch overhead added up (~528 across 16 layers).

Analogy: like 15 small files each making a separate trip to the printer — the walking takes longer than the printing. The fix is to batch what can be batched into one print job.

Optimization (Route 1): every 3 attention heads share the same data, so they stack into one larger matrix multiplication — cutting per-layer launches from 31 to 11 (total ~528 → ~208).

Metric (backbone only, 16 layers)Before optAfter opt
NPU backbone latency~400 ms~226 ms
CPU-NumPy reference latency (same math, fp32)~344 ms~340 ms
NPU / CPU-NumPy ratio1.16× (NPU slower)0.71× (NPU faster)
XRT dispatches / layer33 (31 attention)13 (11 attention)
correctness (make verify)PASSPASS (bit-identical)
Result: the NPU backbone went from 400ms to 226ms (~1.8× faster). After the optimization it beats the NumPy reference (0.71×). Correctness is bit-identical — batching only changes how the work is submitted, not the math.
Two different "CPU backbone" numbers — don't confuse them. Section 4's profiling says the backbone is 56.8 ms; the table above says ~340 ms. Both are correct — they are different CPU implementations: Section 4 is the real LeRobot model (PyTorch, heavily-optimized MKL matmuls), while the table's reference is our own plain NumPy fp32 backbone (cpu_backbone_forward), used only as a like-for-like yardstick for the NPU bench (compile + bridge excluded). So the fair headline is "NPU backbone ≈ 226 ms." Versus the optimized PyTorch backbone (56.8 ms) the NPU is currently slower — expected for an un-fused, first-pass port whose attention still costs 11 dispatches/layer.
Whole-model perspective (from Section 4): the backbone is only 5.8% of the end-to-end CPU time (56.8 of 1044 ms), so speeding it up moves a small slice of the total. A1 proves the method works; the biggest performance prizes are vision (73.6%, milestone A3) and the action expert (20.1%, A2). Remaining backbone headroom: fusing the 11 attention dispatches into the layer's ELF (Route 3).
