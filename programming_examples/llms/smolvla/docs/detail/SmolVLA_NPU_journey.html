1. What is SmolVLA?

SmolVLA is a Vision-Language-Action model (VLA) — think of it as a robot's brain. It comes from Hugging Face's LeRobot ecosystem.

In one sentence: you tell a robot arm "pick up the cube" and give it a few camera views. SmolVLA reads the images + that sentence + the robot's current pose, and outputs a sequence of moves to make next (joint angles, gripper open/close). It fuses "see + understand + decide how to move" into one model.
Inputs / outputs (the lerobot/smolvla_base checkpoint used here, 450M params):
  • Inputs: 3 camera images + one natural-language instruction + a robot-state vector
  • Output: an "action chunk" — it predicts the next 50 steps of actions at once

It generates actions with a method called flow matching: starting from random noise, it iteratively "denoises" over 10 steps into a coherent set of actions — similar to how AI image generators use diffusion, except here what's being "drawn" is robot motion.

2. The three parts of the model

Inside, SmolVLA is three blocks chained like a pipeline:

Why is the backbone a "language model"?

SmolVLA's second block is really a compact large-language model (SmolLM2-360M, same family as Llama). The difference: it doesn't "speak" (it generates no text). Instead it reads the images, text, and state all at once, understands them in a single pass, and hands an "understanding" to the action expert. Because the team has already deployed several models of this kind on the NPU (Llama, Qwen families), this block is the most predictable and the most reusable of existing building blocks — so we tackled it first.

3. Why move it to an NPU? What is an NPU?

CPU vs NPU analogy: a CPU is a versatile generalist — it can compute anything, but only so much at once. An NPU (Neural Processing Unit) is like a workshop built specifically for matrix multiplication — and the vast majority of an AI model's compute is matrix multiplication, so an NPU does it faster and with far less power. A robot needs to react in real time, so moving the model onto an NPU is a key step.

Our chip is the AMD NPU2 (codename Strix, architecture AIE2P), and the compiler toolchain is mlir-air — it translates "one operator in the model" into "a chunk of machine code that runs on the NPU."

4. Full architecture: every step from input to output

This section breaks the whole pipeline down to every module, every kernel, and every tensor shape, so you can judge what can (and already does) map onto the NPU. Every shape below is measured on the real checkpoint (batch = 1), and the data flow was verified against the LeRobot source (modeling_smolvla.py · embed_prefix / embed_suffix) — not inferred from the paper.

Legend: (tensor shape) · has an NPU kernel · no NPU kernel yet (needs new work) · a module is a named sub-network; a kernel is the low-level op that runs on the chip.

How all THREE inputs become tokens (verified)

A common confusion: the vision encoder handles images — but what about the instruction and the state? All three inputs are turned into tokens (fixed-width vectors) and concatenated into one sequence called the prefix. Here is the exact, source-verified flow:

InputModule that embeds itShape flowResult
3 camera images embed_image = SigLIP ViT → connector (see below) (3,3,512,512) → per image (64,960) 3 × 64 = 192 vision tokens
Instruction text embed_language_tokens = a token-embedding lookup table (same one every LLM uses) tokenizer → (1,48) ids → (48,960) 48 language tokens
Robot state state_proj = a single Linear (GEMM) (1,32) → (1,960) 1 state token
Concatenate → the prefix fed to the backbone: (241,960)

So the backbone doesn't just see images — it sees images + words + state as one 241-token sequence. The attention mask (verified in embed_prefix) makes image + language tokens attend to each other bidirectionally, while the state token starts a new block — this is why the backbone's attention is "non-causal," which matters a lot for the NPU mapping (Section 6).

So the action expert is the natural next step (A2). Note: the expert runs 10 times (once per denoise step); the backbone runs only once.

Once you see this whole map, "can it map onto the NPU?" becomes clear: ② the backbone's kernels all exist → done; ③ the expert reuses the same kernels + the existing K/V injection → feasible, A2; ① vision needs 4–5 brand-new kernels + a large attention → hardest, A3.

5. Our approach: a CPU / NPU hybrid

We did not move the whole model onto the NPU. We built a hybrid pipeline: NPU runs the most valuable, most core language backbone; CPU runs the rest. This is a deliberate engineering trade-off, not unfinished work.

What runs where, and why

Model partRuns onWhy
Language backbone (16 layers: norms / projections / attention / activations)NPU2Core, compute-heavy, reuses already-validated kernel building blocks
Vision encoder SigLIP + connectorCPUFrozen, hardest to move (needs 4–5 new kernels), runs once per episode → lowest payoff
Action expert + 10-step denoiseCPUSpecial structure; planned as the next milestone, A2
Final norm, prefix assemblyCPUOutside the per-layer hot loop, same choice as every LLM sibling

Key design: how the non-causal attention was built

The original attention is "non-causal" (within the prefix, image and text tokens can all see each other — unlike GPT, which only looks backward). The NPU's ready-made FlashAttention is hard-wired to be causal and internally complex; reworking it is risky. And the backbone's attention matrix is only 241×241 — small enough to fit in on-chip memory, so FlashAttention's memory-saving tricks aren't needed anyway.

So we compose attention from three simple building blocks: a GEMM for Q×Kᵀ → masked_softmax (a new kernel that handles all heads + the mask in one shot) → a GEMM for probabilities×V. The mask is computed on the host and passed in, so causal, bidirectional, or padding-aware are all possible — flexible and reliable.

Three fused ELFs: one layer = 3 big blocks, not 33 tiny calls

To reduce "dispatch" (job-launch) overhead, each backbone layer's operators are packed into 3 fused NPU programs (ELFs): ① rms_gemms_rope (RMSNorm + QKV + RoPE) ② attention (GEMM + softmax + GEMM) ③ o_ffn (O + residual + RMSNorm + SwiGLU). The first two are reused/adapted from the already-deployed llama/qwen models; the attention is new in this project. The performance work in Section 9 mainly compresses the number of calls inside ② (attention).

③ the action expert and ① vision are still entirely on CPU — no NPU kernel replaces them yet. Section 4 already lists what each needs (expert: reuse backbone kernels + cross-attention wiring; vision: new kernels like conv2d / LayerNorm / GELU-tanh / softmax / pixel-shuffle). Those are the A2 / A3 work.

7. How we mapped the backbone onto the NPU (phase by phase)

We didn't do it all at once. Like stacking bricks, every step was verified correct before adding the next. The process had 4 phases:

0Build a CPU reference (the "answer key")

First run the real SmolVLA on plain CPU and record every layer's output as the "answer key" (oracle). Everything the NPU computes afterward is checked against it. ✅ done

💡 This step already caught a key trap: the config file says the RoPE parameter is 100000, but the code actually uses 10000 at runtime — only found by comparing similarity against the answer key. Using the wrong value would silently corrupt the whole backbone.

1Validate each "brick" kernel

The backbone needs 8 kinds of basic operation (matrix mult, norm, RoPE, activation…). Seven are existing, NPU-validated bricks that just needed re-testing at SmolVLA's new sizes. The only brand-new one is the "non-causal attention" — instead of hacking the complex existing attention, we composed it from "matrix mult + masked softmax," which is more robust. ✅ done

2Assemble ONE layer, check against the answer key

Assemble the bricks into the backbone's first layer, run on the NPU, compare with the answer key's layer 1. Similarity 0.99998 (1.0 is identical) — assembly is correct. ✅ done

3Scale to 16 layers, run end to end

Replicate one layer into the full 16, inject the NPU-computed per-layer K/V "memory" back into the CPU action expert, produce the final action chunk, and compare with the pure-CPU chunk. ✅ done

💡 We also ran a "perturbation test": deliberately replacing the NPU-computed K/V with random noise makes the action chunk change drastically — proving the action is genuinely driven by the NPU's computation, not secretly by the CPU.

9. Performance: before vs after optimization

This project was correctness-first, then optimize speed. On the first measurement the NPU was actually a bit slower than CPU — because the attention part split the 15 "attention heads" into many small jobs sent to the NPU, and the job-launch overhead added up (31 launches per layer, ~500 across 16 layers).

Analogy: like having 15 small files to print, each making a separate trip to the printer — the walking takes longer than the printing. The optimization is to batch what can be batched into one print job.

Optimization (Route 1): among the 15 attention heads, every 3 share the same data, so they can be stacked into one larger matrix multiplication. This cut per-layer launches from 31 to 11, and the total from ~528 to ~208.

MetricBefore optAfter opt
NPU backbone latency (16 layers)~400 ms~226 ms

NPU / CPU ratio1.16× (NPU slower)0.71× (NPU faster)

Result: the NPU backbone went from 400ms to 226ms (~1.8× speedup), and is now faster than the CPU. And the correctness numbers are bit-identical after the optimization — because "batching the launches" only changes how the work is submitted, not the math being computed.
Headroom remaining (not yet done): ~208 launches still remain. The next step (Route 3) would fuse a layer's attention into an even larger NPU program block to cut overhead further. That's a future direction.
