SmolVLA branch — Kernel work on the AMD NPU2

What was built, adapted, and validated at the kernel level on this worktree branch (smolvla)
A companion to the main journey artifact, focused only on kernels: which kernel, which shape, its performance and correctness, and where the implementation came from — so you can understand the branch's kernel contribution without reading the kernel_registry yourself. All numbers are measured on real NPU2 (Strix, AIE2P). Terms explained in the box below.
How to read this (quick glossary):
  • kernel = one low-level op compiled to run on the NPU (a matmul, a norm, an attention block…).
  • shape = the exact tensor sizes the op runs at, written M×K×N for a matmul C[M,N]=A[M,K]·B[K,N], or rows×cols / N for elementwise ops. A kernel must be validated at each shape — "the kernel exists" is not the same as "this shape was tested".
  • kernel_registry = an in-repo catalogue that records, per kernel and per shape, the best measured tile config + performance + accuracy on NPU2, so model code looks up a proven config instead of guessing.
  • mean_rel_L1 = average relative error vs a 32-bit-float reference. Lower = more accurate. ~9e-3 is the standard bf16 matmul tier; ~4e-3 norms; ~4e-2 attention (it chains more rounding).
  • GFLOP/s = compute throughput (higher better, for compute-bound ops like matmul/attention). GB/s = memory bandwidth (higher better, for memory-bound ops like norms/activations/residuals).
  • tiles = how much of the NPU2 compute array the kernel occupies. The chip is an 8 columns × 4 rows = 32-tile array. 8×4 = 32 is full-chip; 8×2 = 16 half; 8×1 = 8 one row; < 8 is under-filled. More tiles is not automatically better — several kernels are physically capped below 32 by a hardware limit, not by a missed tuning opportunity (see §7).

A note on per-kernel vs integrated accuracy. Every kernel here is individually clean at the tiers shown. When the 12 vision layers were first run in sequence as separate dispatches, a tiny systematic bias from the NPU's block-float (BFP16) matmul accumulated and pulled the final encoder output to 0.945 (vs a 0.99 gate). Fusing the per-layer ops into two multi-launch ELFs fixed this — doing the bias-adds and residuals on-device in bf16 removed a host bf16→f32→bf16 round-trip that had been amplifying that bias, lifting the encoder to 0.990 (PASS) while also cutting wall time 2.6×. The integration story is in the main journey artifact (Ch. 7.5 & 10).

1. The big picture — three kinds of kernel work

Mapping SmolVLA onto the NPU almost never required writing a kernel from scratch. The recurring pattern was "the kernel already exists — but this shape has never been run on the NPU." So the work splits into three buckets:

KindWhat it meansOn this branch
NEW write a kernel No implementation existed for the operation we needed. masked-softmax — the one genuinely new kernel (the backbone's non-causal attention needs an arbitrary host mask, which the existing FlashAttention can't express).
EXTEND change a kernel An example existed but lacked a feature or the right layout. LayerNorm — the example did plain normalization; we added the affine weight·x+bias and multi-tile execution the vision encoder needs.
REUSE + VALIDATE run & record a shape A proven kernel, run at SmolVLA's specific shape, measured, and recorded in the registry. Everything else: GEMM, RMSNorm, RoPE, SiLU-and-Mul, Element-wise Add, FlashAttention, GELU-tanh — 16 (kernel, shape) rows across the backbone and vision.
Two "kernels" that turned out to need no kernel at all. The vision patch embedding is a Conv2d, but because its stride equals its kernel size (non-overlapping 16×16 patches), it is mathematically a reshape (im2col) followed by an ordinary matmul — so it reuses the GEMM kernel, no conv kernel. The connector's pixel-shuffle is a pure index remap done on the host. Recognising these saved two kernel builds.

5. The kernels we actually wrote or changed

NEW  masked-softmax — the one from-scratch kernel

Why it was needed. The backbone's attention is non-causal but masked (a "prefix-LM" mask: image + language tokens see each other freely, the state token starts a new block, and padding is excluded). The registry FlashAttention only offers a single boolean causal on/off switch — it cannot express an arbitrary mask. So attention here is done the classic way: scores = Q·Kᵀ (GEMM) → softmax(scores + mask) (this kernel) → P·V (GEMM).

What it is. A full-row softmax that takes a second host-supplied additive-mask input alongside the scores and computes softmax(in + mask) per row. Forked from programming_examples/softmax/ → lives at programming_examples/masked_softmax/.

The subtle bit. A fully-masked row uses the bf16 lowest value (≈−3.4e38) so it softmaxes to a uniform row rather than NaN — but that value overflowed the kernel's exp look-up-table quantizer, so a floor clamp (kExpDiffFloor = −120) was added inside the exp routine. Runs on NPU2, verified PASS.

Source: programming_examples/masked_softmax/ · forked from programming_examples/softmax/

EXTEND  LayerNorm — added affine + multi-tile

Why it was needed. The vision encoder uses LayerNorm (subtract the mean, then scale-and-shift by learned γ, β), unlike the backbone's simpler RMSNorm. The existing programming_examples/layer_norm/ example did the normalization but had no affine parameters and ran on a single tile.

What changed. Added the affine (x−mean)·rstd·γ + β epilogue and multi-tile execution (8 columns of the array). Validated at 1024×768: 324 µs, 9.7 GB/s, accuracy 4.4e-3 (same tier as RMSNorm), then promoted into the registry as a new kernel. A reusable trick fell out of it (see gotchas: packing γ‖β into one buffer to stay under the DMA limit).

PROMOTE  GELU-tanh — validated & added to the registry

What happened. The vision MLP activation is GELU (tanh approximation). The programming_examples/gelu/ example already had the exact math (using the hardware tanh intrinsic), so no code change was needed — it was validated at the vision shape 1024×3072 (24.1 GB/s, 8.4e-3) and promoted into the registry.

A measured surprise. GELU has a single input (unlike the 3-input SiLU/residual kernels), so it fits twice as many tiles on the array before hitting the per-tile DMA limit — a free ~1.8× bandwidth headroom that the "copy the sibling's config" habit would have missed.

COMPOSE  Two fused vision ELFs — many kernels, one dispatch

Why it was needed. Running each vision op as its own NPU dispatch made the encoder host-bound, not compute-bound: 141 ms of actual NPU work was buried under 212 ms of host gap across 121 dispatches (~1.75 ms each of Python + driver overhead). The fix isn't a faster kernel — it's fewer dispatches.

What was built. Two multi-launch ELFs (vit_fused_builders.py, stitched with the same stitch_elf machinery the language backbone uses): vit_ln_qkv (7 launches: LayerNorm + Q/K/V GEMMs + biases) and vit_o_ffn (10 launches: O-proj + residual + LayerNorm + fc1 + GELU + fc2 + residual). Every bias-add and both residuals moved on-device. Result: 121 → 37 dispatches, host gap 212 ms → 4 ms, wall time 2.6× faster.

The bonus. Doing bias/residual on-device in bf16 also removed a host bf16→f32→bf16 round-trip that had been amplifying BFP16's systematic bias — which is what lifted end-to-end accuracy from 0.945 to 0.990 (PASS). A rare case where fusing for speed also bought accuracy.

6. Gotchas found (silent-wrong-answer traps)

Several configs compile and pass their size asserts but produce silently wrong output on the device. These are the most valuable findings — they're invisible without a numeric check against a reference, and they are now documented in the registry so the next deployment avoids them.

Kernel / shapeThe trapThe fix
GEMM, K=960 tile size tile_k_l2=160 silently corrupts (error ≈0.77 — basically garbage), no compile error. Use tile_k_l2 ∈ {64,192,320,960} (we use 320).
Element-wise Add N=245760 Stock tile_n=2048 passes the divisibility assert but zeros most of the output (odd inner-DMA count mis-transfers). Use tile_n=1920 (verified clean).
LayerNorm (4 data streams) input + weight + bias + output = 4 host↔chip DMA streams per tile exceeds the ~3-stream routing limit → compile failure at full width. Pack weight‖bias into one flat buffer → back to 3 streams. Reusable for any multi-parameter norm.
GEMM connector 64×12288×960 Feared the huge K=12288 would fail to place (→ CPU fallback). Then the idle half-array looked like a missed 2×. Both instincts were wrong. K is not the blocker (just more reduction tiles) — places & PASSes, no fallback. And the idle half is not the cost: the op is weight-DMA-bound, so filling it is measurably slower. The real win was the tile width: tile_n 80 → 240 = 1.33× at identical accuracy (§7).
GEMM fc1 1024×768×3072 The standalone test reports FAIL — on 4 of 3,145,728 output elements (0.0001%), all with tiny reference magnitudes (|ref| ≈ 3e-3…9e-6) where the strict high-precision atol = 1.5e-3 bites. Same tolerance-edge class as every Qwen wide-N shape. The high-precision path is numerically correct (mean error 9.4e-3, squarely in tier) and faster (4195 GFLOP/s vs 3650) — deploy it; the 4 elements are a tolerance artifact, not a datapath error.
any kernel, wrong target Building for the default aie2 (NPU1) target silently outputs all-zeros on NPU2. Always build with AIE_TARGET=aie2p for NPU2.
two fused ELFs, different tile_n Two ELFs whose GEMMs use different tile widths (96 vs 128) both resolved to the same generic mm_m32.o object → the second reused the first's stale baked-in width → garbage (similarity 0.07). Key the compiled object name by tile_n so each width gets its own object.

7. Array occupancy — how many tiles each kernel uses, and why

NPU2 is an 8 columns × 4 rows = 32-tile compute array. A kernel that leaves tiles idle leaves performance on the table — but only if those tiles were reachable. On this branch three different ceilings are in play, and it matters which one a kernel hit: a physics ceiling is fine, a tuning ceiling is a bug.

KernelTilesFillCeiling — and is it real?
GEMM (all 8 projection/attention shapes) 8×4 = 32 100% optimal Full chip. GEMM tiles over both M and N, so it always fills the array when M ≥ tile_m·8.
FlashAttention 1024² 12/12 8×4 = 32 100% optimal 12 heads is even → heads_per_unroll = 2 fills all 8 columns. Measured 1.58× vs the half-array config the odd-15-head backbone is forced onto.
GEMM connector 64×12288×960 4×4 = 16 50% ceiling proven, and correct M = 64 caps it at 16 tiles — and 32 tiles would be slower. The microkernel needs tile_m % 16 == 0, so tile_m·herd_m = 64 = M allows at most 4 M-columns; the full grid was enumerated and 4×4 is the maximum reachable. Padding M to 128 to fill 8×4 was measured and is slower in wall-clock. The kernel is weight-DMA-bound, not tile-bound — see the box below.
GELU-tanh 8×2 = 16 50% at its hardware ceiling Single-input op = 2 DMAs/tile, so a second row places where the 3-DMA kernels can't. 8×4 was tried and fails to place. Getting to 16 was worth 1.8× over the 8-tile config a "copy the sibling" habit would have chosen.
RMSNorm · LayerNorm · SiLU-and-Mul · Element-wise Add · RoPE 8×1 = 8 25% at their hardware ceiling All are 3-DMA/tile streaming ops (two inputs + one output, or row + params + output). The shim-DMA channel budget hard-caps them at one 8-column row — herd_y > 1 does not place. Within the row, scaling is near-linear (6.1–7.6× from 1→8 columns), so the 8 tiles they can use are used well.
masked-softmax 1×4 = 4 12.5% a real tuning gap The one kernel not at its ceiling. It inherited the upstream softmax/ herd layout sizes=[1, herd_n] — a single column, 4 rows. Raising herd_n to 8 fails to compile ("row index (6) must be less than the number of rows (6)") because rows max out at 4; the fix is to spread across columns instead, which the current builder cannot express. See below.
Case study — "can we fill 8×4?" answered properly for the connector GEMM. This is the one row where the idle half looked like a missed opportunity, so it was measured rather than argued:
  • 32 tiles is unreachable. Enumerating the whole (tile_m, herd_m, tile_n, herd_n) grid under the microkernel's tile_m%16==0 / tile_n%16==0 and the divisibility asserts gives 4×4 = 16 as the maximum. (tile_n=120 would allow herd_n=8 since 960 = 120·8, but violates n%16 — confirmed by compile failure.)
  • Forcing it is counter-productive. Padding M 64→128 to genuinely fill 8×4 runs 734 µs vs 667–713 µs — slower. The GFLOP/s doubles, but half of it is padding arithmetic.
  • Because the bottleneck is bandwidth, not tiles. The weight matrix is 23.6 MB — 93% of all traffic, and independent of M. 25.3 MB in ~890 µs ≈ 28 GB/s, at the DMA ceiling. Halving K halves the latency (892→518 µs), and the tile sweep 4/8/16 (7358/1668/888 µs) is near-linear then saturates. Idle tiles have no bandwidth left to consume.
  • The sweep did find a real 1.33× — just not from tiles. The registry's tile_n was 80; the sweep is strongly non-flat (16:3352 µs, 48:1347, 80:890, 240:667–713) and tile_n=240 is 1.33× faster at bit-identical accuracy. The 80 came from the generic "N is not 512-aligned → shrink TILE_N" habit, which is the wrong instinct for tiny-M/huge-K: fewer, larger N-tiles amortize the weight stream better. Registry and the deployment path are now both on 240.
The transferable lesson: "fill the array" is a proxy, not the goal. For a memory-bound op, occupancy stops mattering the moment the DMA saturates — check the arithmetic intensity before treating idle tiles as a bug.
The one honest gap: masked-softmax uses 4 of 32 tiles. Every other kernel on this branch is either at 100% or provably at a hardware ceiling. masked-softmax is at 12.5% purely because it inherited the upstream softmax example's one-column herd (sizes=[1, herd_n]) and that layout was never revisited. The sibling elementwise kernels all use sizes=[herd_x, herd_y] and reach 8–16 tiles.

Verified on hardware, not assumed: the deployment-scale run (N = 15·256·256 = 983040, all 15 heads batched into one dispatch) PASSes at herd_n = 4; herd_n = 8 fails to place because the array only has 4 rows. Because it is a 3-DMA/tile op (scores + mask in, probabilities out), its realistic ceiling is the same 8×1 = 8 tiles the other 3-DMA kernels hit — so the available headroom is roughly 2×, not 8×. That is a builder change (swap the herd axis), and it is not yet done.
The reusable rule this produced (now written into the registry's methodology notes): the tile ceiling is set by DMA streams per tile, not by a fixed number. 3 streams → one 8-tile row; 2 streams → 16 tiles. Never inherit a herd config from the nearest-looking kernel — count its DMAs and sweep herd_y yourself. GELU is the proof: assuming SiLU's 8-tile cap would have silently cost 1.8× bandwidth.

Worth stating plainly: masked-softmax — the one kernel written from scratch — is the one thing here that is not in the kernel_registry. It runs, it has a lit test, and it was re-verified PASS on NPU2, but it carries no registry page: no per-shape performance number, no documented tolerance, and no precision report in its harness (it prints only PASS!). In one sentence: on this branch the NPU-kernel effort was overwhelmingly reuse-and-validate — 10 GEMM shapes, plus RMSNorm/RoPE/SiLU/Add/FlashAttention/GELU/LayerNorm shapes measured and recorded — with exactly one new kernel written (masked-softmax) and one extended (LayerNorm gaining affine), which is why the registry grew from 8 to 9 kernel families and now carries every shape SmolVLA's backbone and vision need. On array occupancy, every kernel is at 100% fill or at a demonstrated hardware ceiling — with the single exception of masked-softmax at 4/32 tiles, which is an inherited-layout gap, not a physical limit.
